## 1. プロジェクト概要

### 1-1. 背景

HEW の主題は「お金が動く Web サービス」である。ARGUS は市販の6脚ロボット（Freenove ＋ Raspberry Pi 5、歩行制御は公式コードを無改造で使用）に、自作の **AI レイヤ（画像認識・音声対話）** と **IoT レイヤ（Flask＋SQLite＋取引処理＋Web）** を載せた作品であり、後者がその主題に直接あたる。観客は Web 上でログインして**体験チケット（模擬通貨）**を購入し、それを消費してロボットに指示を出す。購入から消費までの取引はすべてシステムに記録するが、決済は**模擬決済**とし、実際の金銭は動かさない。

### 1-2. 目的

観客はその場で名前と PIN を登録してログインし、公開ページで体験チケットを購入（模擬決済）する。購入したチケットは利用者ごとの残高として管理され、観客はそれを消費して目の前の実機ロボットへ指示を出す。**「ログイン → チケット購入 → 残高加算 → チケット消費（残高減算）→ 取引記録 → 命令キュー → 実行 → 完了記録」の全経路が利用者単位で後から追跡できる**状態で、指示した動作が数秒後に現実で起きる体験を成立させる。

### 対象プラットフォーム（利用端末・ブラウザ）

観客：スマートフォン（iOS Safari / Android Chrome、縦画面）で公開ページを利用／運営：PC の Chrome で管理ダッシュボードを利用／サーバ：PC または Raspberry Pi 5 上の Flask＋SQLite。**会場ローカル LAN のみで動作し、インターネット公開は行わない。**

## 2. 機能要件

### 2-1. Ver1.0 対象機能（スコープイン）

| # | 機能名 | 機能の説明（何ができるか） | 優先度 |
| --- | --- | --- | --- |
| 1 | AI 人物検出とライブ映像 | カメラ映像を配信し、観客がログインなしで視聴できる。AI が人物を検出して時刻・信頼度・静止画・枠座標を保存し、映像の上に検出枠を重ねて表示する | 高 |
| 2 | 会員登録・ログイン | 名前（24文字まで）と4桁の PIN で会員登録・ログインできる。PIN はハッシュ化して保存する。ログイン中は自分の名前とチケット残高を表示し、ログアウトのほか一定時間操作がなければ自動でログアウトする | 高 |
| 3 | チケット購入（模擬決済） | ログイン中の利用者がチケットパック（500チケット ¥500〈模擬〉／1,000チケット ¥1,000〈模擬〉）を選び、確認画面で購入を確定すると購入記録が1件永続化され、残高に加算される。画面には模擬決済であり実際の請求が発生しないことを明記する | 高 |
| 4 | チケット消費と取引記録 | ログイン中の利用者がアクションを選んでチケットを使うと、残高から必要枚数（前進・旋回 100／お辞儀・手を振る 300／人を探す 500）を減算し、取引を1件永続化する。残高不足・未定義のアクションは受け付けない。利用者別の累計ランキングを公開し、運営は購入・検出・取引・命令を1画面で確認できる | 高 |
| 5 | チケット→動作の実行閉ループ | 取引成立と同時に命令キューへ登録され、ロボットが取得して実行し、完了報告で `done` になる。ロボットへ渡すのは成立した取引に紐づく命令のみとする | 高 |
| 6 | 「人を探す」ミッション | チケット消費でミッションが `active` になりロボットが巡回し、AI が人物を発見すると `success` と成功時刻が記録される | 高 |
| 7 | 音声対話と音声操作 | 話しかけると1〜2文で応答し、「何が見える？」には最新の検出結果を参照して答える。動作語は即座に実機へ送る | 中 |

### 2-2. Ver1.0 対象外機能（スコープアウト）

| # | 機能名 | 対象外とした理由 |
| --- | --- | --- |
| 1 | 実際の金銭決済（本番カード決済・外部決済サービス連携・返金） | 模擬決済で主題を再現でき、本番決済の責任を負えないため。また会場ローカル LAN のみで動作させるため外部サービスに接続しない。決済処理は差し替え可能な構造にしておく |
| 2 | パスワード再設定・メール認証・SNS ログイン | 展示当日にその場で作成し数分だけ使うアカウントであり、メール送信や外部認証はインターネット接続を前提とするため |
| 3 | 自律走行・顔認識による個人特定・インターネット公開・録画保存・多言語 UI | 歩行は公式コードを無改造で使う方針であり、その他も展示期間中の価値に寄与せず、リスクと実装コストだけが増えるため |

> ※ 体験チケットの使用管理はシステム上の残高で行い、紙チケットの配布と運営の目視確認は行わない。
> 表示価格は模擬円（1チケット＝¥1〈模擬〉）であり、購入画面に「模擬決済・実際の請求はありません」と明記する。

## 3. 非機能要件

| # | 機能名 |
| --- | --- |
| 1 | 性能：購入・取引 API は1秒以内に応答し、チケット消費から実機動作の開始までを5秒以内とする |
| 2 | 可用性：3モジュールは独立して起動・停止でき、サーバ停止中も他モジュールは異常終了せず復旧後に自動再開する |
| 3 | セキュリティ・データ整合性：PIN はハッシュ化して保存し、ログイン状態はセッションで管理する。ログイン・購入・消費の各 API に試行間隔の制限を設ける。アクションのホワイトリスト検証と入力検証を行い、残高の減算と取引記録は同一トランザクションで確定させて残高が負にならないようにする。購入・取引・命令・ミッションを利用者と時刻付きで永続化して相互に追跡できる |
| 4 | 保守性・運用：モジュール間 API は `CONTRACT.md` を正本とし、実機なしで「ログイン → 購入 → 消費 → 実行」の閉ループを1コマンドで回帰検証できる。ネット不通でも主経路（模擬決済を含む）は動作する。展示用の共用端末では無操作60秒で自動ログアウトし、前の利用者の状態を次の観客に残さない |
